### 3. 接入 /remember 用户记忆

在 [ConsoleCommandHandler](../../HanyingAgent/SRC/Host/Console/ConsoleCommandHandler.cs)
增加命令：

```text
/remember 解释代码时优先使用 C++ 类比
```

当前行为：

- 将明确输入保存为当前可信用户的 User 级 WorkingMemory。
- 复用已有 IWorkingMemoryManager 和内存 Store，不另建一套记忆存储。
- 无须选中 Session，不创建业务 Task，不写入 Conversation，也不调用模型。
- 空白内容拒绝；写入失败或取消不显示成功。
- 使用 Preference 类型，Source 为 `console:/remember`，Confidence 为 1、Importance 为 0.5。
  这些是本命令提供的元数据，不是模型评分；Confidence 不代表内容已被验证为事实。
- 不设置默认到期时间；当前也没有自动分类、去重更新或自动敏感内容识别。
- 纯文本帮助和富终端帮助均补充命令、进程内有效范围与敏感信息提示。

用途限定为非敏感编码偏好和技术约定，不应输入个人信息、密钥或其他敏感内容。
当前没有新增记忆查看、修改或遗忘命令；底层已有相应操作，但 Console 管理入口仍待后续设计。

### 4. 让用户记忆进入实际模型上下文

后续对话自动读取同一用户最近最多 20 条有效工作记忆：

- 通过 LocalUserContext 获取可信 UserId，不从模型输出推导记忆访问范围。
- 仅读取该 User Owner，不自动扩大到其他用户、Session、Task 或 Global。
- 有效状态和到期过滤沿用 WorkingMemory Manager 的既有规则。
- 编排器校验读取结果非空且归属一致，异常、取消或跨归属结果显式失败。
- 记忆在同一进程内跨 Session 可用，不因切换会话而丢失。
- 这是按更新时间读取近期记忆，不是依据当前问题进行向量或语义检索。

预算选择后的输入结构为：

```text
System：系统指令 + 存在记忆时的参考资料使用规则
User：记忆参考数据，采用带标题的 JSON
User / Assistant：选中的历史消息
User：当前输入
```

召回的候选记忆不保证全部进入最终输入，须参与统一预算选择。
记忆正文不提升为系统指令，参考消息不追加到 Conversation。
没有记忆时不插入空参考块，也不额外修改系统指令。
JSON 格式和使用规则不构成模型绝不会服从恶意参考文本的保证。

### 5. 将编排调用扁平化

今天接入记忆时，最初沿用旧结构：

```text
Orchestrator
    → Executor
        → ContextBuilder
            → Memory
```

这种结构隐藏了准备阶段，同时历史由编排器协调、记忆却由 Builder 读取，阅读边界不一致。
最终改为由同一个编排层显式组织平级能力：

```text
DialogueOrchestrator
    → Conversation：保存用户输入
    → ConversationWindow：读取候选历史
    → WorkingMemoryManager：读取当前用户记忆
    → ContextBuilder：统一预算选择，构造 ModelInvocation
    → DirectExecutor：调用模型并解释响应
    → Conversation：保存 Assistant 回复
```

对应调整：

| 组件 | 最终职责 |
|---|---|
| [DialogueOrchestrator](../../HanyingAgent/SRC/Runtime/Agent/Orchestration/DialogueOrchestrator.cs) | 协调数据读取、上下文构造、执行和回复保存。 |
| [BuildContextRequest](../../HanyingAgent/SRC/Contracts/Agent/Context/Operations/Requests/BuildContextRequest.cs) | MemoryOwners 替换为明确的 MemoryItem 列表 Memories；后续增加可选的请求级字符保护上限。 |
| [LocalContextBuilder](../../HanyingAgent/SRC/Runtime/Agent/Context/LocalContextBuilder.cs) | 接收候选数据，校验、去重排序、统一预算选择、格式组装和最终校验，不依赖 Memory 服务。 |
| [DirectExecutor](../../HanyingAgent/SRC/Runtime/Agent/Execution/DirectExecutor.cs) | 接收已构造的 ModelInvocation，调用一次模型并解释结果，不再依赖 ContextBuilder。 |
| [ApplicationHost](../../HanyingAgent/SRC/Host/ApplicationHost.cs) | 同步新的构造依赖和 DI 组合。 |

MemoryOwners 的移除是请求协议变更，调用方和 JSON 测试已同步修改。
旧 JSON 只有 MemoryOwners 而缺少必需的 Memories 时明确失败，不悄悄按空记忆处理。

扁平化针对模块协调边界，不是把所有 Store 和 Provider 的内部调用都搬到 Orchestrator。
模块仍封装自己的实现细节，没有新增转发层、策略工厂或通用协调框架。

### 6. 明确阶段状态与日志关联

- WaitingForModel 改为在 Context 构造成功后、进入 Executor 前更新。
- 记忆读取或 Context 构造失败时，不调用模型，也不提前标记为等待模型。
- ReadMemory、BuildContext 和 WaitForModel 的已知异常由编排边界记录阶段，再原样向上传播。
- Execute 阶段仍由执行器记录相关异常，避免编排层重复记录。
- Context 构造现在发生在 Executor 的 ExecutionId 范围之前，使用外层 SessionId、
  以及任务入口已有的 TaskId 关联；Executor 与模型日志额外携带 ExecutionId。
- 记忆读取和 Context 构造后检查取消，避免依赖忽略取消、正常返回后继续进入模型。

### 7. 将对话阶段提取为 private 方法

在扁平编排基础上，进一步提取：

```text
SaveUserAsync
SelectHistoryAsync
ReadMemoryAsync
BuildContextAsync
NotifyWaitingForModel

```

模型执行直接复用已有的 `executor.ExecuteAsync`。
RespondCoreAsync 保留步骤顺序、phase 标记、资源范围和异常边界，
先通过方法名理解“做什么”，再按需进入实现理解“怎么做”。

不会因阶段辅助方法返回而提前释放。已有取消、失败、不保存 UnsupportedAction 为纯文本历史、
以及回复保存失败不重试模型等行为保持不变。

### 8. 将历史与 Memory 的预算统一收归 Context

接入 Memory 后进一步发现，原先的容量管理存在职责问题：

```text
ConversationWindow 先按完整字符额度选择历史
  → ContextBuilder 再追加 Memory 和参考格式
  → 合计超限时直接失败
```

旧窗口已经按轮数、字符数限制历史，并不是聊得足够久就必然失败；
但它不知道后续记忆的开销，不能独立决定占用整个输入额度。
本次将“各模块提供候选，Context 决定最终带入内容”落实到代码。

#### 模块职责调整

- [ConversationWindow](../../HanyingAgent/SRC/Runtime/Agent/Context/ConversationWindow.cs)
  只读取并转换候选完整问答轮次，不再接收系统指令和字符预算。
  保留默认最多 10 轮、可配置 1–100 轮、每页 20 条、最多扫描 200 条的候选读取限制。
- DialogueOrchestrator 继续扁平调用历史、Memory 和 Context，不把外部数据读取嵌套回 Builder。
- BuildContextRequest 的 Messages 现在要求历史由完整 User / Assistant 轮次组成，
  最后是一次当前 User 输入；可选 MaxInputCharacters 只能收紧 Builder 的字符保护配置。
- LocalContextBuilder 统一选择 History 与 Memory，完整保留系统指令和当前输入。

#### 模型级预算与可替换计数能力

新增：

- [ModelTokenBudget](../../HanyingAgent/SRC/Contracts/Agent/LanguageModels/Models/ModelTokenBudget.cs)：
  表达配置模型的窗口、输出预留、安全余量以及是否估算。
- [IModelTokenCounter](../../HanyingAgent/SRC/Contracts/Agent/LanguageModels/Operations/IModelTokenCounter.cs)：
  解析模型预算，对完整输入消息计数或估算。
- [ConservativeModelTokenCounter](../../HanyingAgent/SRC/Infrastructure/LanguageModels/ConservativeModelTokenCounter.cs)：
  当前使用的可替换保守估算器，不新增 tokenizer 依赖或模型词表下载。

```text
可用输入 Token = 模型窗口 − 输出预留 − 安全余量
默认配置：4096 − 256 − 128 = 3712
可选上下文额度 = 可用输入额度 − System 和当前输入开销
```

当前按每 UTF-8 字节估算一个 Token，另加每消息 8、整个请求 8 的协议余量；
这不是匹配模型 tokenizer 的精确计数，也不是任意聊天模板都不会超限的保证。
日志通过 TokenCountIsEstimate 明确标识，不冒充 Provider 返回的实际 ModelUsage。
Host 为计数器和 Ollama 调用适配器使用相同的模型名称及窗口配置；
请求覆盖为未配置预算的其他模型时明确拒绝，不悄悄套用默认模型额度。

显式 MaxOutputTokens 保留；未指定时在最终 ModelInvocation 中补齐预算使用的默认值，
确保实际发送的输出上限与预留空间一致。
原有默认 32,000 UTF-16 正文长度限制作为额外保护继续存在，与 Token 估算共同约束候选选择。

#### History / Memory 保留份额与借用

按确认的策略实现：

- 必需内容占用后，剩余可选预算默认分给 History 75%、Memory 25%；字符保护额度也按相同比例分配。
- 双方先在各自份额内选择，份额不会随着历史轮数增加而变化。
- 空闲份额可以互相借用，一方没有候选时另一方可以使用全部剩余额度。
  双方均有候选但一方用不完时也可借用；借用阶段先尝试补充记忆，再扩展历史。
- 历史从最近向更早选择完整问答轮次；遇到放不下的轮次停止，不拆分或跳过它拼接更早历史。
- 记忆按更新时间倒序、ID Ordinal 升序逐条尝试；超大条目整条省略，可继续尝试后面的较小条目。
- 份额是预算保留，不保证任意大小的条目都能放入；极大记忆仍可能无法进入上下文。
- 试选和最终校验均计入参考规则、标题、JSON 元数据及转义等开销。
- 省略只影响本次模型上下文，不删除 Store 记录，也不截断用户输入或记忆正文。
- 必需的 System 与当前输入本身超限才因预算失败；非法数据、协议或计数能力错误仍明确传播。

新增 Agent 配置 HistoryBudgetPercent（默认 75，范围 1–99）和 TokenSafetyMargin（默认 128，非负）。
启动校验输出预留与安全余量之和必须小于模型窗口。
事件 2003 改为报告候选轮数和扫描情况；事件 2002 报告最终选中、省略数量、
输入 Token 估算与额度、输出预留、历史份额及是否估算，不记录正文。
契约、模块、Host、Console、模型适配、日志、测试说明和对话类图均同步更新。

## 学习与设计讨论

### 业务任务和后台执行的边界

- CreateTask 登记 TaskInfo、建立任务和会话索引、占用 Session，本身不启动 Agent。
- 共享 Gate 保护“检查空闲、创建任务、绑定会话”整组操作，不只是保护单个字段。
- TransitionTask 校验预期状态，不覆盖已进入 Cancelling 的任务。
- TaskInfo 是可查询的业务快照，ExecutionHandle 是本进程的执行控制资源，二者通过 TaskId 关联。
- 控制链和后台执行链可以 await 同一个取消回调 Task；等待不会重复执行回调。
- User / Session / Task 是记忆归属范围，不等于长期 / 短期，也不等于持久化方式。

### 单 Agent 优先

讨论了 Agent 定义、独立执行上下文、多 Agent 分工与上层协作的可能建模。
当前决定仍是完善唯一 Agent，不引入 Agent、AgentRun 或多 Agent 调度对象。
这些讨论不表示项目已经实现了相应类型或能力。

### 单次对话与 ReAct 的流程层级

- 当前 RespondCoreAsync 是一次用户输入到回复的外层流程，只调用一次模型。
- 未来 ReAct 应在内部循环“构造 Context、调用模型、处理工具请求及结果”，
  而不是每次模型调用都重复保存用户输入、重新执行完整对话入口。
- 每次模型调用前需要包含最新执行记录的上下文；Memory 是否重新召回应由编排器明确决定。
- 当前要求最后一条为 User 是纯文本对话实现的约束，不是所有模型调用的通用要求；
  工具循环中最后一条可能是 Tool 结果，届时需同步调整协议。
- 提取 private 阶段方法已有可读性收益，不意味着必须引入继承式模板方法；
  当前没有多个实现共享固定流程骨架，暂不增加抽象基类。

### 容量来源与分配策略分离

模型侧提供“模型有多大窗口、如何计数或估算”，Context 决定“这次容量如何分配、最终带哪些内容”。
只有历史一种主要可选来源时，在历史窗口内计算容量是自然的最小实现；
加入 Memory 后继续在那里占用整个额度，就会让局部决策挤占其他上下文来源。
未来 Skills、工具定义与工具结果也应参与 Context 的统一预算，而不是各自计算一套总额度。

### 自动提取与记忆整合尚未实现

当前机制是：

> 手动记住，自动读取。

普通输入只进入 Conversation，不自动变成 Memory。
后续需要分别设计：

1. **Conversation 到候选记忆**：识别值得保留的结论、技术约束或编码偏好，
   区分讨论中的方案与已确认决策，保留来源，明确适用范围。
2. **候选审核与写入**：检查重复、更新和冲突；可先采用自动建议、用户确认，
   不让模型自行决定访问范围或直接写入权威记忆。
3. **短期到长期整合**：按稳定性、复用价值和可信证据筛选、合并，不是简单复制或延长到期时间。
4. **更新和遗忘**：定义信息失效、旧结论被替代以及到期后清理的规则。
5. **失败策略**：记忆处理失败是否影响主任务需要明确，不应因此重新调用已经完成的主模型请求。

以上是讨论方向，没有新增自动提取、用户确认流程或长期记忆实现。
