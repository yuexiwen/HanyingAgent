## 今天完成了什么

### 1. Conversation 只承担历史管理

原 DialogueCoordinator 虽然位于 Conversation，但实际协调了输入保存、历史选择、
执行器调用和回复保存，属于跨模块流程，不是历史数据管理。

将其与配套请求移出后，[Conversation](../../HanyingAgent/SRC/Capabilities/Conversation/Conversation.md)
保留：

- LocalConversationManager：消息追加、查询、归属、幂等与顺序规则。
- IConversationStore：历史存储端口。
- ConversationHistoryReader：面向历史查看的分页与轮数选择。

Conversation 不依赖执行器，不驱动模型调用。历史数据管理与 Memory 类似，
但交互记录和记忆仍是不同的数据模型与生命周期，不合并为通用存储模块。

### 2. Tasks 独立管理任务生命周期

将原 Orchestration 中的任务实现迁入独立的
[Runtime/Tasks](../../HanyingAgent/SRC/Runtime/Tasks/Tasks.md)：

| 文件                                                                                | 职责                                                       |
| ----------------------------------------------------------------------------------- | ---------------------------------------------------------- |
| [LocalTaskManager](../../HanyingAgent/SRC/Runtime/Tasks/LocalTaskManager.cs)         | 接受任务、后台执行、查询、取消、等待、终态保存及停止收尾。 |
| [ITaskStore](../../HanyingAgent/SRC/Runtime/Tasks/ITaskStore.cs)                     | 任务状态、结果及 Session 占用的原子存储端口。              |
| [TaskExecutionOptions](../../HanyingAgent/SRC/Runtime/Tasks/TaskExecutionOptions.cs) | 不依赖 Host 配置类型的不可变执行参数。                     |

任务生命周期不再作为 Orchestration 的子职责目录。
ExecutionHandle 仍由 LocalTaskManager 管理，跟踪实际执行与取消资源，收尾后移除并释放；
任务记录及最终结果仍由 Store 保存。

对应任务测试迁至 [TEST/Tasks](../../HanyingAgent/TEST/HanyingAgent.Tests/Tasks/TaskTests.cs)，
同步调整测试命名空间。

### 3. Orchestration 专注对话流程

将 DialogueCoordinator 更名为
[DialogueOrchestrator](../../HanyingAgent/SRC/Runtime/Orchestration/DialogueOrchestrator.cs)，
与 [DialogueRequest](../../HanyingAgent/SRC/Runtime/Orchestration/DialogueRequest.cs)
直接放在 Orchestration 根目录，不再保留额外的 Dialogue 子目录。

职责链路：

```text
Tasks / LocalTaskManager
  → 创建执行 Scope，调用 DialogueOrchestrator
      → Conversation：保存用户输入
      → Context / ConversationWindow：选择并转换历史
      → 阶段回调：由 Tasks 更新 WaitingForModel
      → Execution / DirectExecutor
          → Context Builder：构建模型请求上下文
          → 模型适配器：调用模型
      → Conversation：保存 Assistant 回复
      → 返回 ExecutionOutcome
  → Tasks 解读执行结果或异常
  → 保存任务终态、释放会话、清理执行句柄
```

Orchestration 不反向依赖 Tasks 的具体实现，不直接修改 Task Store；
通过已有阶段回调报告进度，由 Tasks 决定任务状态转换。
DialogueRequest 名称保留，执行方法和运行逻辑未改动。

### 4. Conversation 迁入 Capabilities

进一步明确：Runtime 负责推进执行，Conversation 与 Memory 一样，为运行流程提供数据支撑，
因此将历史管理从 Runtime 迁入 Capabilities，而不是继续作为运行流程模块。

- LocalConversationManager、IConversationStore、ConversationHistoryReader 和模块文档迁入
  Capabilities/Conversation，命名空间改为 HanyingAgent.Capabilities.Conversation。
- ConversationWindow 仍属于 Runtime/Context，负责模型预算下的历史选择，而不是历史存储。
- 公共协议仍在 Contracts/Conversation，具体存储仍在 Infrastructure/Persistence。
- 同步更新 DI 所用类型引用、Host、Persistence、测试、应用说明及相关文档链接，
  不改变消息保存、读取、身份校验或任务执行行为。
- Capability 指运行流程可复用的能力，不等同于暴露给 LLM 的 Tool。
- 当前本地历史管理仍依赖 Runtime.Users.LocalUserContext 获取可信身份；
  本次没有引入身份抽象，也不代表已完成全部依赖解耦或独立服务部署。

## 学习与设计结论

- 业务 Task 与 .NET Task 不同：前者是工作记录与状态，后者表示异步操作。
  ExecutionOutcome 是执行策略结果，TaskResult 是任务管理层保存的最终业务结果。
- Console 的 Completion 是自定义属性，类型为 Task<TaskResult></taskresult>；
  IsCompleted 包括正常、异常及取消，await 负责取得结果或传播异常。
- Console 使用一次 ReadLine 对应一个输入 Task，并与后台结果一起参与 WhenAny。
  后台结果先到不会丢弃原读取，处理输入后才清空引用并开始下一次读取。
- 显示 You> 只是提示，不代表一定创建新读取；当前并非完整终端编辑器。
- 当前目录结构可作为后续扩展基线，但目录清晰不等于已完成远程服务化：
  仍需针对真实替换需求明确契约、超时、取消、幂等和一致性。

### 已识别但本次未修复的 Console 问题

- Displayed 去重集合会持续增长：需要结合 Pending、Unread、显式等待及会话切换，
  明确标记何时能安全清理，不能随意删除导致重复展示。
- ReadLine 当前按行提交，不支持将多行作为一个问题。
  后续需先确定显式多行模式还是终端编辑器方案，再实现输入收集和提交边界。
- 通知到达时 read 可能已经完成，提示符逻辑仍可能多换行或重显；
  用户输入不会因此自动丢失，但当前不具备精确光标检测与输入行重绘。

这些是讨论中识别的后续事项，本次未调整其行为。
