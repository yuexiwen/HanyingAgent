## 一、架构认识与设计结论

### 1. 三类流程职责

| 层次 | 职责 | 当前对应 |
|---|---|---|
| 入口适配 | 接收用户操作、解析输入并展示结果。 | Console 入口。 |
| Task Lifecycle Flow | 接受任务、管理会话占用、安排执行、查询取消、保存终态和收尾。 | Management/Tasks。 |
| Agent Execution Flow | 协调历史、记忆、Context、模型执行及回复保存。 | Agent/Orchestration。 |

```text
Console，或未来的 REST API
  → ITaskManager
  → Task Lifecycle Flow
      → Agent Execution Flow
      → 根据执行结果保存业务终态并清理资源
```

等待终端输入或接收 HTTP 请求属于入口适配，不是任务生命周期本身。
未来可以替换入口并复用后面的业务流程，但远程入口仍需单独处理认证、授权、
传输错误及调用取消与业务取消的区别。本次没有创建 HTTP 入口。

### 2. 控制面与数据面是另一种观察角度

- **Control Plane Data**：User、Session、Task 的身份、归属和运行状态。
- **Data Plane Data**：Conversation、Memory、本次 Context，以及未来的工具结果和产物。
- User → Session → Task 主要表达归属，不是线程执行层级。
- 两类数据并非完全隔离，例如 Task.Input 也承载实际内容，Conversation 通过 SessionId、TaskId 关联管理数据。
- Console 可以通过业务接口查看历史或显式写入记忆；数据面不等于禁止用户访问。
- 两类数据也不等于两种存储方式：Context 通常是临时调用快照，其他记录可以采用内存或未来的持久化实现。

因此，不把三个流程层次和两类数据直接建立为五个并列目录。

### 3. TaskManager 不负责底层线程调度

结合 [LocalTaskManager](../../HanyingAgent/SRC/Runtime/Management/Tasks/LocalTaskManager.cs)
明确了业务 Task 与 .NET Task 的关系：

- TaskInfo 是业务快照，ExecutionHandle 是本进程执行控制资源。
- Work 初始指向 Task.CompletedTask，只是非空的已完成占位，不启动工作。
- Task.Run 安排后台入口，返回的 Task 保存到 handle.Work，跟踪整个 RunAsync 异步执行链。
- await handle.Work 等待执行链结束，不重新执行，也不只等待异步委托返回。
- 业务失败可以被记录为 Failed 后正常完成 Work；Work 完成不等于业务成功。
- TaskManager 安排入口和管理生命周期，实际代码调度由 .NET 运行时及线程池负责。
- 将来的业务排队、并发限制与优先级，不等于重新实现线程池或 async/await 调度器。

### Agent 内部的四类职责

| 类别 | 职责 |
|---|---|
| Orchestration | 决定步骤顺序、分支和未来的循环，显式协调平级模块。 |
| Execution | 控制模型调用策略并解释响应，当前为 DirectExecutor。 |
| Context | 统一预算、选择候选信息并组装模型输入。 |
| Capabilities | 提供对话、记忆、技能和工具等信息与操作能力。 |

Capabilities 不命名为 Data：Memory 有管理规则，Tools 也有实际动作的执行能力。
工具定义和工具结果可以成为 Context 输入，但工具执行者本身不等于纯数据源。
Provider 协议和具体存储仍在 Infrastructure，不因归入 Agent 而混入编排实现。

## 三、Contracts 同步分层

[Contracts](../../HanyingAgent/SRC/Contracts/Contracts.md) 按相同职责组织：

- [Management](../../HanyingAgent/SRC/Contracts/Management/Management.md)：
  Users、Sessions、Tasks。
- [Agent](../../HanyingAgent/SRC/Contracts/Agent/Agent.md)：
  Context、Execution、LanguageModels、Capabilities。
- Agent/Capabilities：Conversation、Memory、Tools；Skills 尚无实际契约，不创建空目录。
- 每个领域继续按需保留 Models、Operations、Requests、Responses。
- 不为镜像实现目录而增加 Contracts/Agent/Orchestration、Host 或 Infrastructure 协议层。
- Agent 契约可以引用 Management 的 UserId、SessionId、TaskId 表达归属。
- IUserStore、ITaskStore、IConversationStore 等内部存储端口仍与所属模块放在一起，
  不因为它们是接口就全部公开到 Contracts。

目录迁移同时修改 namespace、using、类型引用和组合根所需引用，例如：

```text
HanyingAgent.Runtime.Management.Tasks
HanyingAgent.Runtime.Agent.Orchestration
HanyingAgent.Runtime.Agent.Capabilities.Memory
HanyingAgent.Contracts.Management.Sessions.Models
HanyingAgent.Contracts.Agent.LanguageModels.Models
```

这是 C# 源码引用路径的变更；JSON 字段、role 判别值、状态枚举和业务协议语义保持不变。
后续外部调用方引用旧命名空间时需要同步调整。

## 六、讨论但未实现的后续方向

- Conversation → Memory 是提取与整合，不是把历史搬走；原始 Conversation 应保留。
- 提取模块可以先在当前 Project 内通过接口读取、生成候选并确认写入，
  无须等待文件持久化；存储方式、触发方式和部署方式是三个独立维度。
- 将来需要批量处理、跨重启恢复或资源隔离时，再决定是否独立 Worker；
  独立进程不能直接访问当前进程的内存数据。
- 自动记忆提取、长期整合、ReAct、工具执行、HTTP 入口和远程身份授权均未在本次实现。
