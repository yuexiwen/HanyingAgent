## 一、Tool 与 MCP 的关系

Tool 是具有定义的可调用能力，定义用于说明名称、用途和输入参数。
本地工具通过对象方法执行；MCP 将工具发现与调用等交互做成标准协议。

MCP 不等于“远程 Tool”：stdio 可以连接本机独立进程，HTTP 才涉及网络服务接入。
MCP 除工具外还包含资源、提示等能力，本期统一入口只封装工具发现与调用。

`ModelContextProtocol.Protocol` 是官方 C# SDK 中存放协议数据类型的命名空间，
不是协议标准本身。Tool、ListToolsRequestParams 和 CallToolResult 是协议消息对应的 C# 类型；
SDK 负责握手、序列化和实际通信，应用不自行实现 JSON-RPC。

## 二、统一客户端与每个 Server 的连接

本次统一术语：

- **统一客户端**：应用侧的 McpToolClient，维护统一的访问方式。
- **连接管理器**：McpConnectionManager，管理多个 Server 的连接与生命周期。
- **SDK Client**：每个 Server 对应的 McpClient，表示独立协议会话。

因此，不是应用必须为每个 Server 创建一个统一入口，
而是一个统一入口内部管理每个 Server 各自的连接。

```text
应用调用方（未来可以是 Agent）
    ↓
McpToolClient
    ↓
McpConnectionManager
    ├─ Server A 的 Connection → McpClient → Server A
    └─ Server B 的 Connection → McpClient → Server B
```

注册配置、建立连接和发现工具是三个不同阶段，不能混为一谈。
不同 Server 可以提供同名工具，通过 ServerName + ToolName 区分，不互相覆盖。

### 配置和 DI

[ApplicationHost](../../HanyingAgent/SRC/Host/ApplicationHost.cs) 使用配置绑定机制填充 McpSettings，
注册连接管理器与统一客户端为 Singleton，并将同一个管理器注册为 HostedService。

McpSettings 是数据容器，不主动读取配置。
DI 注册只是登记创建方式；管理器实例被创建时才执行构造函数。
Host 启动会解析 HostedService，从而提前完成配置校验，但不会连接 Server。

构造函数为每个 Server 创建配置快照和 Connection 管理对象：

```text
_connections[serverName]
    ├─ Options：校验并复制后的配置
    ├─ Gate：该 Server 独立的访问锁
    └─ Client：初始为 null
```

Arguments 和 Environment 分别复制为新的集合，避免外部修改原配置影响后续连接。
Server 名称使用 Ordinal 比较，区分大小写；重复名称、空命令、非法超时、
非法环境项或非现有绝对工作目录明确拒绝，禁用项也需要通过配置校验。

应用依赖增加官方 ModelContextProtocol.Core 2.4.0；
测试 Server 使用 ModelContextProtocol 2.4.0 的 Hosting 扩展。
[appsettings.json](../../HanyingAgent/appsettings.json) 默认 `Mcp.Servers` 为空，不启动外部进程。

## 四、第一次连接、复用与失败

第一次 ListToolsAsync 或 CallToolAsync 进入 ExecuteAsync 后：

```csharp
connection.Client ??= await ConnectAsync(connection.Options, waiting.Token);
```

`??=` 表示只有左侧为 null 时才执行右侧并赋值；它本身不是并发锁。
第一次访问会创建连接，后续访问复用已保存的 Client。

ConnectAsync 先用配置创建 StdioClientTransport，再调用：

```csharp
var client = await McpClient.CreateAsync(
    transport, clientOptions, loggerFactory, cancellationToken);
```

创建 transport 只是准备传输对象；CreateAsync 才通过传输启动 Server 子进程、
建立 stdio 通信并完成协议握手。它返回 Task<McpClient></mcpclient>，
await 成功后得到已连接的 Client，再保存到 Connection。

完整流程：

```text
配置绑定 → 校验与快照 → 建立 Connection 管理对象
    → 第一次访问 → 创建 SDK Client 并握手
    → 保存 Client → 执行工具发现或调用
```

如果连接失败：

- await 抛出异常，不会得到有效 Client，也不会完成该赋值。
- ExecuteAsync 记录日志并原样传播异常，finally 释放 Gate。
- 本次请求不自动重试；Client 仍为空，后续新请求可以再次尝试连接。
- SDK 负责初始化失败时的会话与传输清理，本次测试验证了握手超时和取消后的进程退出。

已连接的 Client 若被 SDK 确认结束，后续新请求会先释放旧 Client 再重新连接。
这不等于重试正在失败的工具调用，不能盲目重复可能产生副作用的操作。

## 五、委托、Lambda 与闭包的理解

ListToolsAsync 和 CallToolAsync 都调用 ExecuteAsync，只是传入不同的操作函数。

```csharp
Func<McpClient, CancellationToken, Task<T>> operation
```

这是一个委托类型的参数，表示“可以作为参数传递的行为”：

- 输入参数一：McpClient。
- 输入参数二：CancellationToken。
- 返回类型：Task<T></t>；Func 的最后一个类型是返回类型。

ExecuteAsync 准备好连接和请求令牌后执行：

```csharp
return await operation(connection.Client, request.Token);
```

它对应调用方传入的：

```csharp
async (client, token) =>
{
    // 使用连接执行操作。
}
```

参数按位置对应：connection.Client 传给 client，request.Token 传给 token。
client 和 token 是匿名函数的参数，不是外部自动生成的变量。
函数体使用外层的 serverName 等变量才属于闭包捕获。
委托也可以指向签名匹配的普通方法，不一定必须是 Lambda 或闭包。

### 两个箭头的区别

```csharp
public Task<IReadOnlyList<Tool>> ListToolsAsync(...) =>
    _connections.ExecuteAsync<IReadOnlyList<Tool>>(...);
```

外层 `=>` 是表达式方法体，等价于方法体中直接 return ExecuteAsync 返回的 Task。
内层 `async (client, token) => { ... }` 则是作为参数传入的匿名异步函数。
传入函数时并不直接执行它；连接管理器在准备完成后调用它。

这可以从策略模式的角度理解，也可以称为委托式公共流程封装：

```text
固定流程：获取锁 → 准备连接 → 设置超时 → 执行操作 → 释放锁
变化行为：发现工具 / 调用工具
```

传统策略模式常用接口与实现类，本次用委托和 Lambda 表达可替换行为。
用 C++ 的经验类比，它更接近能够保存捕获型 Lambda 的 std::function，而非单纯函数指针。

**连接管理器决定“如何执行”，传入的函数决定“执行什么”。**

## 六、工具发现与调用

### ListToolsAsync

传入的异步函数检查 Server 是否声明 Tools 能力，然后分页读取并合并工具定义：

```text
Cursor = null 请求第一页
    → 收集 page.Tools
    → 用 page.NextCursor 请求下一页
    → 无 NextCursor 时结束
    → 返回合并后的工具列表
```

分页用于兼容工具较多的 Server，不代表所有 Server 必须分页。
每页数量由 Server 决定，我们的请求不指定 PageSize，也不假设固定数量。
游标是不透明标记，客户端只原样传回，不解释或修改其内容。
Server 一次返回全部工具且没有 NextCursor 时，循环只执行一次。
HashSet 记录已返回的下一页游标，重复时明确失败，避免循环请求。

返回原始 Tool 定义和 Schema；每次发现重新请求，不建立应用侧工具目录缓存。

### CallToolAsync

校验工具名称，复制参数顶层字典，再由 SDK 调用指定工具。
嵌套可变参数仍由调用方管理，不是深复制。
返回原始 CallToolResult，保留 Content、StructuredContent 和 IsError。
工具层 IsError 返回给调用方判断；协议错误、未知工具和连接失败明确传播。
本次未加入 Task / Session 归属校验或 MCP 到 ToolObservation 的转换，
这些属于未来业务适配，不放进连接管理器。

## 七、Gate、并发与一致性

### 为什么当前有 Gate

每个 Connection 有独立的：

```csharp
public SemaphoreSlim Gate { get; } = new(1, 1);
```

初始许可数与最大许可数都是 1。
WaitAsync 获取许可，已占用时异步等待；finally 中 Release 归还许可。

它主要防止：

1. 两个首次请求同时发现 Client 为空，重复创建连接或 Server 进程。
2. 请求使用连接时，另一个操作同时替换或释放连接。

当前锁覆盖整个请求、连接替换与清理，因此同一 Server 的访问串行，
不同 Server 的访问可以并发。这是本次简化生命周期管理的选择，不是 MCP 的要求。

本次讨论了更细粒度的未来方案：保护连接创建，允许正常调用并发，
释放时协调进行中的请求。不能只把 Release 提前，否则连接可能在使用期间被释放。
**该方案本次仅讨论，没有修改当前串行实现。**

### MCP 是否支持并发：三层回答

1. **协议层**：支持多个未完成请求，通过请求 ID 匹配各自响应，
   不保证执行或完成顺序。
2. **实现层**：Server 可以同时处理，也可以内部排队；实现本身需要具备相应的并发安全性。
3. **业务语义层**：并发结果与副作用是否符合调用方约定；有共享可变状态时，
   需要按要求采用锁、事务、版本检查、幂等或隔离等机制，不是所有工具都必须满足完整 ACID。

只读工具通常适合并发，但数据被同时修改时结果可能不同。
有状态工具也不一定不能并发，关键是是否涉及冲突，以及 Server 是否保证业务正确性。
限制单个客户端的并发不能限制其他客户端，不替代 Server 的一致性保障；
通常应协调冲突操作，而不是一律禁止整个 Server 的并发。

### 共享可变状态与一致性

共享可变状态是多个请求共同访问的同一份可修改数据，
例如配置、文件、数据库记录或外部资源，不局限于内存字段。

这里的一致性指多个操作交错执行后，数据和行为仍符合约定。
例如计数器初始为 10，两个“加 1”都读取 10 再写入 11，最终只增加一次，
这就是丢失更新；若约定两次增加都应生效，正确结果应为 12。

一致性不必然等于“所有读取都拿到最新值”：

- 同时读写时，读取修改前或修改后的完整值可能都合法。
- 若要求修改成功后必须读到新值，需要先等待修改完成，并由 Server 提供相应保障。
- 一次修改多个字段时，还可能要求不读到部分更新的混合状态。

**并发是否安全，应看结果是否符合业务语义，而不是仅看工具有没有状态。**

## 八、超时、停止和安全边界

- 连接超时覆盖连接与握手；请求超时从连接成功后开始，
  覆盖一次调用或完整工具分页，不包含排队时间。
- 请求令牌关联调用方取消、Host 停止和请求超时；排队也能由调用方或停止令牌取消。
- 取消本地等待不保证 Server 已停止操作或撤销副作用。
- Host 停止后拒绝新请求，取消进行中的访问，等待释放 Gate 后清理 Client；
  清理支持幂等异步释放与现有 Host 的同步 Dispose。
- 清理异常显式记录并聚合，不因一个连接清理失败而跳过其余连接。
- stdio 执行宿主权限下的本地程序，不是沙箱，只配置经过批准的可信 Server。
- 进程继承 SDK 的基础环境白名单，再应用显式 Environment，不整体复制宿主环境。
  显式环境仍可能传递敏感值，不将秘密提交到配置文件。
- stdout 只用于 MCP 协议，Server 日志写 stderr；SDK 和外部日志不保证自动脱敏。
- 公共入口当前依赖 SDK 协议类型，属于基础设施 API，不是 Agent 公共契约。

## 十、当前边界与学习结论

本次已实现：

```text
配置 → Server 连接管理 → 统一工具发现 / 调用 → 原始 MCP 结果
```

尚未实现 HTTP、认证、动态注册、多用户连接隔离、sampling、elicitation、
Agent 工具调用循环或 MCP 业务适配。没有改变 DirectExecutor 的模型调用行为。

本次形成的核心理解：

> McpSettings 由 Host 配置绑定填充数据；McpConnectionManager 在实例创建时
> 管理配置组成的 Connection，第一次访问才真正创建 Client；
> McpToolClient 封装应用访问入口，通过不同委托实现工具发现和调用。

**配置描述“连接谁”，管理器负责“如何管理连接”，委托描述“拿到连接后做什么”。**
