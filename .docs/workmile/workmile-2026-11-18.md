## 今天完成了什么

### 1. 梳理任务模块及输入后的调用链

明确以下概念：

- TaskId / TaskInfo / TaskStatus 表达业务任务标识、快照和状态。
- TaskResult 是最终业务结果；.NET Task / Task<T> 表示异步操作，二者不是同一个概念。
- ExecutionHandle 是本地执行控制资源，保存 Work、取消源及取消回调，不是业务记录。
- LocalTaskManager 实现 ITaskManager，提供任务操作；同时实现 IHostedService，
  在 Host 启动时允许接受任务，停止时拒绝新提交、请求取消并等待收尾。
- `_accepting` 只控制接受新任务，不是查询等全部接口的总开关。
- ITaskManager 和 IHostedService 注册指向同一个管理器实例，不能分别创建两套运行状态。

整理后的普通问题处理主线：

```text
ConsoleApplication 读取一行
  → ConsoleCommandHandler 区分命令和普通输入
  → LocalTaskManager.SubmitAsync
      → Store 创建任务并占用会话
      → 创建执行句柄，启动后台 RunAsync
      → 返回接受快照
  → Console 保存结果等待，继续接收输入

后台 RunAsync
  → DialogueOrchestrator
      → Conversation 保存 User
      → ConversationWindow 选择历史
      → 阶段回调，由 Tasks 更新 WaitingForModel
      → DirectExecutor
          → Context Builder 组装模型输入
          → Ollama 模型适配器调用 HTTP
      → Conversation 保存 Assistant
      → 返回 ExecutionOutcome
  → Tasks 保存 TaskResult 与终态、释放会话
  → 清理执行句柄
  → Console 的结果等待完成，展示回答或其他会话通知
```

提交与后台执行是分开的；Console 不是从接受输入开始一直同步等待模型。
当前对话路径传入空 MemoryOwners，不自动召回记忆。

### 2. 从集中式 Store 改为独立接口实现

原 InMemoryDialogueStore 同时实现四个 Store 接口，用户、会话和历史集中在主文件，
任务操作放在 Tasks 分部文件中。阅读时不容易按模块定位，名称也不足以表达实际职责。

今天先尝试更名为 InMemoryAgentStore，并按接口拆分 partial 文件；
随后进一步确认：partial 只拆文件，没有拆开类职责，不符合当前希望按模块独立替换存储的方向。
**最终不保留这个中间方案，也不增加实现全部接口的组合转发类。**

最终结构：

```text
Infrastructure/Persistence
├── InMemoryUserStore.cs
├── InMemorySessionStore.cs
├── InMemoryConversationStore.cs
├── InMemoryTaskStore.cs
├── InMemoryAgentState.cs
├── InMemoryWorkingMemoryStore.cs
└── Persistence.md
```

| 实现 | 实现的接口 | 职责 |
|---|---|---|
| [InMemoryUserStore](../../HanyingAgent/SRC/Infrastructure/Persistence/InMemoryUserStore.cs) | IUserStore | 用户新增、读取、列举和资料更新。 |
| [InMemorySessionStore](../../HanyingAgent/SRC/Infrastructure/Persistence/InMemorySessionStore.cs) | ISessionStore | 会话创建、读取、关闭、隐藏及独立对话 lease。 |
| [InMemoryConversationStore](../../HanyingAgent/SRC/Infrastructure/Persistence/InMemoryConversationStore.cs) | IConversationStore | 消息追加、幂等校验、顺序及历史分页。 |
| [InMemoryTaskStore](../../HanyingAgent/SRC/Infrastructure/Persistence/InMemoryTaskStore.cs) | ITaskStore | 任务创建、状态转换、取消请求、结果保存及分页。 |

[ApplicationHost](../../HanyingAgent/SRC/Host/ApplicationHost.cs) 分别注册四个 Store 单例，
管理器直接注入各自接口，不经过统一大类。Store 之间不持有或调用其他 Store。
工作记忆仍使用原有独立实现，本次不更改其行为。

### 3. 用内部共享状态保留原子操作

[InMemoryAgentState](../../HanyingAgent/SRC/Infrastructure/Persistence/InMemoryAgentState.cs)
承担当前内存适配的共享数据及同步边界：

- 保存用户、会话、隐藏标记、消息、历史、任务、结果和会话任务索引。
- 提供同一个 Gate，以及跨数据的会话归属、可写状态及任务归属校验。
- 不实现 Store 接口，不持有 Store，不转发业务调用，不作为统一业务入口。
- 四个 Store 通过内部构造函数接收同一份状态，由组合根通过工厂完成注册。
- 每个 Host 容器有独立状态，不采用静态集合或全局锁。

全部相关读取、校验和写入仍处于同一个 Gate 内，保持：

```text
创建任务 + 占用 Session
保存结果 + 更新任务终态 + 释放 Session
追加消息 + 校验当前 Task / Session 关联
关闭会话与提交任务之间的互斥
```

因此，本次不是把原有原子操作拆成多个各自加锁、可能部分成功的方法调用。
分页、幂等、归属校验、取消、隐藏及迟到终态处理的既有语义保持不变。

需要明确：**独立 Store 类不等于数据已经完全解耦。**
当前内存实现仍共享数据一致性域，跨数据操作仍然访问必要的关联状态。
该状态对象只是当前适配器的内部实现，不是未来所有存储方式都必须使用的公共抽象。
