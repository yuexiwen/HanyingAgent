## 一、Orchestration 与 Execution 的职责调整

### 调整原因

未来 ReAct 可能在一个业务 Task 中多次调用模型。
每次新增工具结果后，都需要重新构造 Context，因此需要明确谁拥有完整执行策略。

两种方案均可成立：

- Orchestration 拥有策略循环，Execution 只负责单次模型执行。
- Execution 拥有完整策略，Orchestration 负责公共准备与收尾。

本次选择第二种方案：

> Orchestration 读取初始信息并保存最终回复；
> Execution 从第一轮开始协调 Context 构造和模型执行；
> Context 独立维护预算、选择与组装算法。

不能同时让编排器和执行器各自拥有一套 ReAct 循环。
本次仅落实 Direct 的边界，没有实现 ReAct、策略工厂或通用执行器框架。

### 修改后的调用链

```text
Management/Tasks
  接受任务、占用 Session、安排后台执行
      ↓
DialogueOrchestrator
  保存 User
  读取候选历史
  读取当前 User 的有效工作记忆
      ↓
DirectExecutor
  调用 ContextBuilder，取得 ModelInvocation
  构造成功后通知 WaitingForModel
  调用模型，解释 ModelResponse
  返回 ExecutionOutcome
      ↓
DialogueOrchestrator
  保存 Assistant
      ↓
Management/Tasks
  保存 TaskResult 和终态、释放 Session、清理执行资源
```

### 具体代码变化

| 组件 | 调整 |
|---|---|
| [DialogueOrchestrator](../../HanyingAgent/SRC/Runtime/Agent/Orchestration/DialogueOrchestrator.cs) | 移除 IContextBuilder 依赖及 BuildContextAsync、NotifyWaitingForModel 辅助方法；将初始材料与回调交给执行器。 |
| [DirectExecutor](../../HanyingAgent/SRC/Runtime/Agent/Execution/DirectExecutor.cs) | 注入 IContextBuilder；ExecuteAsync 从接收 ModelInvocation 改为接收 BuildContextRequest，并支持可选的 waitingForModel 回调。 |
| [ContextBuilder](../../HanyingAgent/SRC/Runtime/Agent/Context/LocalContextBuilder.cs) | 算法未修改，仍负责统一输入预算、历史与记忆选择、最终模型请求构造。 |

复用已有 BuildContextRequest，不新增另一套重复的执行输入模型。
历史与 Memory 获取仍在编排器；DirectExecutor 不直接读取 Store 或 Memory 服务。

这是调用边界与方法签名的变化，不是模型 HTTP 协议、命令或任务状态枚举的变化。
直接调用 DirectExecutor 的代码需同步传入构造材料。

## 二、取消、失败和日志行为

- WaitingForModel 仍在 Context 构造成功后、调用模型前通知，
  不将记忆读取或 Context 构造时间计为等待模型阶段。
- 构造前后检查取消，回调后再次检查取消，再进入模型调用。
- Context 构造失败或观察到取消时，不调用模型，不自动重试。
- Context 构造现在位于 ExecutionId 日志范围内，同时继承外层 SessionId / TaskId。
- 构造失败由执行边界记录并原样传播，编排器不重复记录。
- 因此 Context 失败的边界事件从 DialogueFailed 改为 ExecutionFailed；
  相关取消事件也由执行边界按主动取消或依赖取消区分。
- 历史读写、Memory 读取等编排阶段仍由编排边界记录。
- 保存回复失败不重新调用模型；任务终态保存和 Session 释放规则保持不变。

## 四、讨论形成的数据管理边界

完整记录见 [Execution、Context、State、Conversation 与 Memory 的职责](../discussion/2026-11-21-execution-context-state-and-memory.md)。

| 模块 | 核心问题 |
|---|---|
| Users / Sessions | 谁在使用系统，交互属于哪个会话？ |
| Tasks | 工作是否被接受、运行、取消或结束？ |
| Conversation | Session 中发生过什么交互？ |
| Memory | 哪些事实、偏好、约束和经验值得复用？ |
| Execution/State | 当前执行到哪里，继续执行需要什么中间数据？ |
| Context | 这次模型调用实际应该看到什么？ |
| Persistence | 上述数据如何保存，怎样落实存储一致性？ |
| ConsoleState | 界面选中了什么、结果是否展示过？ |

### 多轮任务的中间数据

为未来 ReAct 讨论确定的默认方向：

- 用户输入与最终回答进入跨任务 Conversation 历史。
- 中间模型可见响应、工具调用与结果供当前 Task 后续推理使用。
- 如需追踪或恢复，可另外保存执行轨迹或检查点，
  但不因此默认加入下一 Task 的候选对话历史。
- Execution/State 承载执行位置及继续执行所需的数据；
  轨迹偏向排错与审计，不能等同于可恢复状态。
- 中间信息中值得复用的内容，可以经过提取与校验写入 Memory，
  不是把整个执行状态搬进 Memory。
- 工作对象在执行真正结束后释放；轨迹与最终结果另设保留规则。
  取消请求本身不允许提前清理仍在使用的执行数据。

这些是设计结论，不表示当前已支持工具历史、任务恢复或执行轨迹存储。

### Memory 范围与读取时机

- 契约支持 Global、User、Session、Task；范围不直接决定保存期限。
- Orchestrator 已有 TaskId，可以读取 Task Memory；
  新任务可能没有记忆，不等于无法读取。
- 公共准备阶段可以形成初始快照，Executor 可在需要时补充或刷新。
- 允许两层访问 Memory，不意味着当前 DirectExecutor 必须新增 Memory 依赖。
- 当前仍只读取用户级最近有效工作记忆，没有实现所有范围的自动合并。

### 相关性召回与搜索推荐

Memory 可以承担类似搜索推荐的候选召回与排序：

```text
用户问题 / 当前子目标
    → 限定允许范围
    → 关键词、倒排、向量或混合检索
    → 有效性过滤与排序
    → Context 按预算选择
```

归属决定允许查询什么，相关性决定哪些有用，预算决定最终放入多少。
Memory 不只是搜索，也负责写入、更新、来源、有效期和遗忘。
Conversation 不只是展示，而是有序交互记录；Memory 可以保留指向原始交互的来源。
当前没有相关性检索、自动提取或长期整合。

### 长对话的 Context 管理

Session 历史超过窗口后，每次请求模型仍需检查并选择 Context。
这不要求每轮扫描全部历史：

- Task 开始时读取候选历史与 Memory。
- 后续轮次在初始快照上追加当前任务记录，再构造输入。
- 必要时明确刷新或补充信息，不默认重复读取。
- 预算包含系统指令、工具定义、消息与工具结果，并预留输出空间。
- 剔出 Context 不等于删除原始数据。
- 未来工具记录应保持调用与结果关联，不能为压缩随意留下孤立结果。
- KV 缓存减少重复计算，不扩大上下文窗口。
