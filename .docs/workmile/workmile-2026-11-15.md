## 今天完成了什么

### 1. 会话连续编号与按编号选择

- `/sessions` 在每个可见会话前显示从 1 开始的连续编号，保留 `*` 当前选择标记和任务摘要。
- `/use INDEX` 可以直接按编号切换；`/use 完整ID` 仍可使用。
- 编号按当前可见列表解析，不是永久标识；新增或隐藏会话后，列表和编号可能变化。
- 跨调用保存引用仍应使用 SessionId，不能把界面编号当作业务主键。

### 2. 删除命令采用“隐藏而非物理删除”

按讨论确定的语义，`/delete INDEX` 只将会话从可见列表隐藏：

- 隐藏后立即显示重排后的列表，编号没有空洞。
- 隐藏当前会话会清除 Console 当前选择。
- 会话、历史、任务和正在进行的执行都保留。
- 完整 SessionId 仍可查询和选择；按完整 ID 选择不会自动取消隐藏。
- 隐藏不是关闭，不取消运行任务，也不改变原来的占用和收尾规则。
- Store 校验会话归属，重复隐藏幂等。

实现落在 [会话契约](../../HanyingAgent/SRC/Contracts/Sessions/Operations/ISessionManager.cs)、
[LocalSessionManager](../../HanyingAgent/SRC/Runtime/Sessions/LocalSessionManager.cs) 与
[InMemoryDialogueStore](../../HanyingAgent/SRC/Infrastructure/Persistence/InMemoryDialogueStore.cs)，
不是单纯在 Console 中过滤显示。
当前没有恢复显示或物理删除命令；内存进程退出后也不会保留这些数据。

### 3. 按对话轮数查看历史

| 命令 | 行为 |
|---|---|
| `/history` | 当前会话最近 1 轮。 |
| `/history 10` | 最近 10 轮，不足则显示全部已有轮次。 |
| `/history all` | 全部历史。 |

一轮按一个 User 输入及其对应 Assistant 回复理解，不按天数或单条消息数量计算。
未回答的输入也计为一轮，展示时明确提示没有记录回复，不虚构回答。

- 数量只接受正整数或 `all`，非法参数明确报错。
- 内部按稳定游标向前读取，每页最多 200 条记录。
- 找到需要的 User 轮数后停止，最终按时间顺序展示。
- 全部历史会读取全部记录；分页读取不等于限制最终返回集合的内存占用。
- 展示历史与送给模型的历史窗口不是同一件事，查看全部不代表全部进入模型 Context。

### 4. 拆分 ConsoleApplication

原来命令解析、查询、状态、渲染和输入结果协调集中在一个类中，阅读成本偏高。
今天采用少量职责明确的组件，不引入每命令一个类或通用命令框架：

| 组件 | 责任 |
|---|---|
| [ConsoleApplication](../../HanyingAgent/SRC/Host/ConsoleApplication.cs) | 初始化 Console，协调单个输入读取与任务结果，处理通知、错误和退出收尾。 |
| [ConsoleCommandHandler](../../HanyingAgent/SRC/Host/Console/ConsoleCommandHandler.cs) | 解析命令和参数，查询数据、调用管理器、更新 Console 选择及展示标记。 |
| [ConsoleRenderer](../../HanyingAgent/SRC/Host/Console/ConsoleRenderer.cs) | 展示提示、会话、任务和历史，不查询 Store 或推动业务状态。 |
| [ConsoleState](../../HanyingAgent/SRC/Host/Console/ConsoleState.cs) | 当前会话、最近任务、待展示结果、未读与已展示标记。 |
| [ConversationHistoryReader](../../HanyingAgent/SRC/Capabilities/Conversation/ConversationHistoryReader.cs) | 可复用的历史分页与最近 N 轮选择，不解析命令或输出终端文本。 |

三个 Console 专属组件放在 [Host/Console](../../HanyingAgent/SRC/Host/Console/Console.md)，
每次 RunAsync 创建一组，共享本次交互状态与输出通道。
历史读取位于 Runtime/Conversation，由 DI 注册，不依赖 Console。

职责边界：

- CommandHandler 发起业务操作，但不直接改写 Session / Task 的权威状态。
- Session 占用和 Task 生命周期仍由管理器与 Store 维护。
- 后台执行不直接写终端，保留主循环统一展示。
- 自动回答、跨会话未读结果、展示去重、取消和退出语义保持不变。
- 没有为本次重构新增业务状态机、事件总线或额外执行入口。

同步更新了[应用说明](../../HanyingAgent/HanyingAgent.md)、
[Host](../../HanyingAgent/SRC/Host/Host.md)、[Conversation](../../HanyingAgent/SRC/Capabilities/Conversation/Conversation.md)
及会话模块说明。

## 启动方式与业务运行时的边界

当前启动链路：

```text
Program → ApplicationHost 创建 DI / Host → 启动服务
        → ConsoleApplication.RunAsync → 停止 Host
```

[Program](../../HanyingAgent/Program.cs) 负责命令行进程的启动和停止；
[ApplicationHost](../../HanyingAgent/SRC/Host/ApplicationHost.cs) 是组合根，注册配置、模型适配、Store、管理器及后台任务服务。
ConsoleApplication 是这一启动方式选用的交互适配器，仍然可以有 Console 自身的输入与通知循环，
但不应成为 Runtime 业务入口的必经层。

目标形态：

```text
Console 入口 / Console 交互 ─┐
                            ├→ 共享 Session / Task / Conversation 协议
GUI 入口 / GUI 交互 ─────────┘   → Runtime → Infrastructure / Capabilities
```

GUI 可以独立启动同样的本地 Runtime，不必先建设服务端，也不必复用 Console 的输入解析和 Renderer。
共享业务能力不代表共享“当前选中会话”等界面状态，各交互入口应拥有自己的状态。
若未来两个独立进程需要共享数据，当前内存 Store 不够；这是另一个需求，不由入口拆分自动解决。

当前尚有耦合：ApplicationHost 同时注册公共服务与 Console 的 TextReader、TextWriter、ConsoleApplication，
Console 层仍依赖具体 LocalTaskManager。不能把本次拆分宣称为完整的多前端架构。

## 用户数据的用途与本地边界

今天澄清了 UserId 的主要用途：

1. 服务端用户资料、认证与授权的关联键；当前本地实现没有完成这些服务端能力。
2. 确定 Session 的归属，作为相关访问校验的依据。
3. 作为用户级 Memory 的归属与检索维度，尤其适用于长期信息。

UserId 不是凭证；用户级 Memory 的归属范围也不等于长期保存期限。
注册一个 LocalUserContext 单例表示当前容器共享可信本地身份，不表示所有存储结构只能容纳一个用户。
当前仍采用本地单用户交互，不扩展登录、角色和多租户；
也没有因为存在 UserId 就自动接通用户长期记忆召回。

## 后续规划

### 第一优先级：收口交互入口边界

1. 先理解并确认 Console → 管理器 → Store / 执行器的调用链，避免把命令类当业务服务。
2. 将 ApplicationHost 的注册按“公共 Runtime 服务”和“Console 专属服务”划分；
   保留单一公共注册来源，不为 GUI 复制一套 Store、模型和 Task 注册。
3. 检查 Console 所用能力能否通过已有 ITaskManager 等协议表达，
   在接口覆盖现有行为时改为依赖协议，不盲目新增通用 ApplicationService。
4. 公共服务注册不得要求 Console.In / Out 或创建 ConsoleApplication。
   GUI 的调度、绑定和当前选择属于 GUI 适配层；后台任务生命周期仍由 Host 管理。
5. 对新增的非 Console 组合方式做最小验证：不注册终端 I/O 也可启动业务服务、
   创建会话、提交及等待任务，并正确停止。保留现有 Console 回归。

这一步不要求立刻开发完整 GUI，也不要求创建 Web API。
GUI 框架和独立启动项目在真正开始图形界面时再选择。

### 第二优先级：建立可理解、可交付的稳定节点

1. 人工验证会话编号、隐藏当前会话、隐藏运行中会话、跨页历史和自动结果展示。
2. 跟读 ConsoleApplication → CommandHandler → LocalTaskManager →
   DialogueCoordinator → ConversationWindow → DirectExecutor，复述正常、失败、取消路径。
3. 发布前执行全套 Release 回归；提交与推送仍按明确请求进行。
4. 暂不增加永久编号、恢复隐藏、物理删除或多用户登录，避免扩大当前任务。

### 第三优先级：实现首个受控工具闭环

继续上一阶段 MCP 计划，但业务能力不能写进 Console：

1. 先探测所选 Ollama 模型的真实工具调用能力；当前适配器拒绝工具请求，连接 MCP 本身不够。
2. 选择一个只读、可预测的工具和一个 MCP Server，明确允许的名称、输入及预期结果。
3. 在工具与适配模块落实发现、参数校验、调用、超时、取消和明确错误。
4. 补齐工具调用与结果消息、CallId 关联及 Context 转换。
5. 在 Execution 实现有限的模型 → 工具 → 结果 → 再推理循环，限制次数与时间。
6. 复用现有 Task 生命周期与 Session 占用，Console 只提交任务并展示结果；
   同一能力未来能由 GUI 发起。

暂缓持久化、跨进程共享、服务端认证、多服务器、任意 Shell 和有副作用的工具。
任务订阅、GUI 进度、流式输出等在具体前端需求明确后设计，不先引入大型事件框架。

## 下一里程碑验收目标

> 公共 Runtime 可以在没有 Console 组件的情况下启动并执行任务；
> Console 继续通过同一业务协议管理会话、提交任务和展示结果。

随后工具里程碑：在同一 Task 生命周期内调用一个允许的只读工具，
依据真实结果回答，失败与取消可追踪，会话可继续使用。

**今日让 Console 更易理解；下一步让它真正成为可替换的交互入口，而不是业务运行时的依赖。**
