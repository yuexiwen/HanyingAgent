## 一、设计目标与基本认识

从一个简单工具开始，但新增工具不应要求修改管理器的分发代码。
因此采用“公共能力入口 + 本地实现协议 + 具体工具”的结构，而不是不断增加 switch 分支。

一个 Tool 是具有结构化描述的可调用能力：

- Definition 描述名称、用途、输入 JSON Schema，以及副作用和可选超时。
- 具体实现校验参数并执行实际操作，返回 ToolResult。
- LLM 只提出工具调用请求，不直接执行函数，也不决定是否有权限执行。
- Agent 运行流程负责补充可信上下文，再由工具管理器校验和分发。

一个具体工具类封装 Definition 和执行入口，但可以包含多个辅助方法。
不同的独立工具可以共享底层业务逻辑，不必重复实现。

## 三、注册、发现与分发

### 注册和启动校验

[ApplicationHost](../../HanyingAgent/SRC/Host/ApplicationHost.cs) 注册：

```csharp
builder.Services.AddSingleton<ILocalTool, GetCurrentTimeTool>();
builder.Services.AddSingleton<IToolManager, LocalToolManager>();
builder.Services.AddHostedService<ToolRegistrationValidator>();
```

LocalToolManager 接收 IEnumerable&lt;ILocalTool&gt;，DI 自动收集所有已注册的工具实例。
工具名称使用 Ordinal 比较，重复名称明确报错，不覆盖已有注册。

AddSingleton 和 AddHostedService 登记创建方式，不表示当场实例化工具。
Host 启动时创建 ToolRegistrationValidator；它依赖 IToolManager，促使容器创建 Manager 和具体工具，
从而在启动阶段发现重复名称、非法定义等问题，而不是延后到第一次调用。
Validator 不执行工具，不提供后台循环；实际校验发生在 Manager 构造函数中。

新增工具的步骤：

1. 在 Implementations 中实现 ILocalTool。
2. 定义唯一名称、描述和输入 Schema，实现参数校验与执行。
3. 在 Host 增加 `AddSingleton<ILocalTool, YourTool>()`。
4. 添加相应行为测试，无需修改 Manager 的分发逻辑。

注册为单例的工具必须支持并发调用，不能在实例字段中保存不隔离的单次调用状态。

### 发现

ListDefinitionsAsync 返回可用定义，按工具名称 Ordinal 升序排列。
AllowedTools 可以缩小本次返回范围，空列表表示不返回工具；未知名称明确报错。

当前授权基线是：当前本地用户拥有的活动任务可以使用所有已注册工具。
AllowedTools 不是授权令牌，也不会保存为后续调用的任务白名单。

### 调用

```text
InvokeToolRequest
  → 校验用户、Task、Session 和活动状态
  → 按工具名查找已注册实例
  → 校验 JSON 对象并登记 Call ID
  → ILocalTool.InvokeAsync
  → 检查 ToolResult
  → 返回关联原调用的 ToolObservation
```

InvokeToolRequest 包含可信的 SessionId、TaskId 和 ToolCallRequest。
未来接入模型时，模型适配器从 LLM 响应解析 ToolCallRequest，
Agent 执行流程补充 SessionId、TaskId；不能让 LLM 决定身份与任务归属。
当前调用请求由测试直接构造。

## 四、时间工具

工具名为 `get_current_time`，输入 Schema 为：

```json
{"type":"object","properties":{},"additionalProperties":false}
```

只接受 `{}`，拒绝数组、额外参数或非法 JSON。
结果 Content 是包含 utcTime 的 JSON，使用 UTC 和往返日期格式。

```json
{"utcTime":"2026-11-25T07:00:00.0000000+00:00"}
```

以上是格式示例。正式 DI 使用系统 TimeProvider；测试使用固定时间，避免依赖测试运行时刻。

## 五、公共调用约束

- Session、Task、Call ID 和工具名称必须有效；Task 必须存在，且用户与 Session 归属匹配。
- 只允许 Running、WaitingForModel、WaitingForTool 状态的任务执行工具。
- 通用入口校验参数为合法 JSON 对象，具体工具负责校验自身 Schema 的语义。
  没有引入通用 JSON Schema 校验依赖。
- 同一 Call ID 在单例 Manager 生命周期内只允许执行一次。
  并发、完成、失败或取消后的重复调用均拒绝，避免因异常或超时盲目重复副作用。
- 调用记录只在内存中保留，没有自动清理，也不跨重启；不代表持久化的 exactly-once 保证。
- Timeout 通过关联 CancellationToken 请求协作式取消，不强制终止线程。
  不响应取消的工具仍可能继续运行，不能将超时等同于动作已停止。
- ToolResult 的失败或未知结果必须提供 Error；不自动将异常转换成成功结果，不自动重试。
- Content 直接用作 Observation.Summary，Content 与 Error 合计最多 8192 个 UTF-16 字符。
  超限明确失败，不静默截断；Artifact 输出尚未实现。
- Observation 保留原 Call ID、工具名、状态、错误、时间戳和耗时。
- 任务状态在调用前检查，不与整个工具执行保持同一把锁。
  调用方仍需传入业务取消 Token，支持执行期间的协作取消。

## 七、当前边界与后续方向

本次实现的是：

```text
代码调用 IToolManager → 本地工具执行 → ToolObservation
```

尚未实现完整闭环：

```text
工具定义交给 LLM
  → LLM 提出工具调用请求
  → Agent 补充上下文并调用 ToolManager
  → 工具结果追加到模型上下文
  → 再次调用 LLM
  → 生成最终回复
```

后续需要另行处理模型协议适配、工具消息的 Context 与预算支持、执行策略循环及调用次数限制。
本次没有修改 DirectExecutor 或模型调用行为，也没有添加 Console 手动执行命令。
