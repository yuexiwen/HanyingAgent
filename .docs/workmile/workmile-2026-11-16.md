### 3. 运行时控制 ILogger 控制台日志

按确认的需求，关闭范围包含所有标准 ILogger 控制台日志，而不只是 Information：

| 命令 | 行为 |
|---|---|
| `/logs` | 查询当前日志开关。 |
| `/logs off` | 关闭标准 Console Provider 的所有日志级别，包括 Warning、Error、Critical。 |
| `/logs on` | 打开开关，恢复按原有日志级别与分类配置输出，不强制启用 Trace。 |

实现与边界：

- 新增 [ConsoleLogControl](../../HanyingAgent/SRC/Host/Console/ConsoleLogControl.cs)，
  以线程安全状态配合标准 LoggerFilterOptions 筛选，不另造 Logger。
- [ApplicationHost](../../HanyingAgent/SRC/Host/ApplicationHost.cs)
  注册单例，Console 命令与日志筛选共享同一开关。
- 已创建的 ILogger 也随开关立即改变是否启用；保留原有规则、分类及级别约束。
- 作用于当前进程全部会话和后台任务，默认开启，不修改配置文件，重启恢复开启。
- 不影响其他日志 Provider；回答、任务结果、失败提示、帮助等交互输出仍然可见。
- 关闭前已进入控制台队列的日志可能继续输出，开关不清空历史或队列。
- 非法参数明确报错，不改变开关，也不输出成功提示。

## 今日设计认识：MCP、工具与 RAG

以下是讨论结论，不代表对应能力已实现：

- MCP Server 可以是独立于 HanyingAgent 的项目，承载检索或其他业务能力，
  通过 stdio 或 HTTP 等方式提供服务。
- Agent 内部通过工具契约表达发现与调用，在工具管理及适配层处理名称映射、
  参数、权限、超时、取消和结果，不把 MCP 协议细节散落到 Console 或执行策略。
- RAG 全称 Retrieval-Augmented Generation，即检索增强生成，是
  “检索 → 将结果加入上下文 → 生成”的流程，不天然等于某一个独立模块。
- 知识检索服务可经 MCP 暴露；接入 MCP 本身不等于已完成 RAG，更不等于模型已能调用工具。
- 固定流程可以在模型调用前检索；工具式流程由模型提出检索请求，再由程序受控执行。
  二者适用场景不同，不能假设模型决定检索总比固定流程准确。
- 知识库与长短期记忆是不同来源和生命周期的数据。
  Context 根据召回结果组装上下文属于增强环节；只有组装本身，不是完整 RAG。

## 后续工作建议

以下是建议顺序，不代表已经实施或用户已决定扩大范围。

### 第一优先级：收口可替换交互入口

1. 将 ApplicationHost 注册拆为公共 Runtime 服务与 Console 专属服务，
   公共注册不依赖 Console.In / Out、渲染器或 Console 日志开关。
2. 检查 Console 对 LocalTaskManager 的具体依赖，优先使用能覆盖现有行为的公共契约，
   避免为 GUI 复制业务逻辑或提前新增通用服务层。
3. 验收无 Console 组件时仍能创建会话、提交并等待任务、取消与停止；
   保留现有 Console 回归，未来 GUI 复用协议而非解析终端输出。

### 第二优先级：稳定当前交互节点

1. 在真实终端验证宽窄窗口、中文、长回答、含 Markup 字符的正文以及重定向输出。
2. 联合验证 `/help`、日志开关、跨会话结果通知、失败与取消；
   关闭日志后仍应明确展示任务失败，而不是伪装成静默成功。
3. 扩展 Runtime 或准备发布前执行全套 Release 回归。
   当前不为提示行交错引入完整终端编辑器，也不顺带增加更多会话管理功能。

### 第三优先级：一个受控的 MCP 工具闭环

1. 先验证目标模型与 Ollama 的真实工具调用能力；当前模型适配器仍拒绝工具请求。
2. 选择一个只读、可预测的工具及 MCP Server，明确工具名、输入、结果和允许范围。
3. 通过既有工具契约接入发现与调用，落实参数校验、超时、取消和明确失败；
   业务实现保留在独立服务或工具侧。
4. 补齐模型工具调用与结果消息、CallId 关联和 Context 转换。
5. 在 Execution 中实现有次数和时间上限的“模型 → 工具 → 结果 → 再推理”循环，
   复用当前 Task 生命周期和 Session 占用，不在 Console 推进执行状态。
6. 如果选择知识检索工具，再以真实召回结果验证工具式 RAG；
   不先建设名为 RAG 的通用大模块，也不把模型生成的链接当作检索证据。

持久化、精确 Token 预算、长期记忆自动召回、流式输出、GUI 和跨进程共享仍属后续议题，
按具体需求分别设计，不与首个工具闭环同时扩张。
