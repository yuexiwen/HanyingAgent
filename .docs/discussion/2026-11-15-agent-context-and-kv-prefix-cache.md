# Agent 上下文与 KV 前缀缓存

讨论日期：2026-11-15

本文整理从 Agent 的职责理解，到应用与推理服务的边界、Token 计量、前缀缓存原理及相关算法练习的讨论。
这是学习记录，不表示 HanyingAgent 已实现 KV 缓存或语义回答缓存。

## 一、从对 Agent 的理解开始

最初的理解：

> LLM 根据本次输入推理；用户却需要能联系前文的交互，所以 Agent 负责保存信息、
> 构造上下文，补齐这个 gap。

这个理解抓住了 Agent 的上下文连续性。
进一步扩展，Agent 不仅让模型知道之前发生了什么，还需要组织工作：

```text
用户目标 → 构造上下文 → 模型推理
                         ↓
                  回答或提出行动
                         ↓
                  执行工具、观察结果
                         ↓
                    必要时再次推理
```

- LLM 是智能能力核心。
- Runtime 是流程与执行控制核心。
- 有上下文的聊天是基础；受控行动、失败处理和取消等，使系统能够持续推进任务。

| 模块 | 解决的问题 |
|---|---|
| Session | 交互归属、隔离和会话占用。 |
| Conversation | 保存已经发生的输入、回复，以及未来的工具调用与结果。 |
| Memory | 保存并召回值得跨轮次、跨会话使用的信息，不仅是历史对话。 |
| Context | 决定本次推理看到什么，控制输入预算。 |
| Task / Orchestration | 管理工作执行、状态、结果、失败和取消。 |
| Tools / Execution | 获取新事实、采取行动并组织推理闭环。 |

这些模块不都是为了添加前序对话；有些负责信息，有些负责可靠执行。
例如，即使一个任务没有历史输入，也仍然需要状态、取消和结果交付。

## 二、Agent 服务与 LLM 提供方的功能边界

### 模型本身

对于这里讨论的常见推理方式，模型依据本次有效上下文生成输出。
普通推理不会把用户对话写进模型权重，也不会自主保存应用级 User、Session 或 Task。

### Agent 或模型服务的应用层

两者都可以提供会话历史保存、Memory 管理、历史筛选、摘要和上下文构造。
因此，客户端只发送会话 ID 和新问题，不代表模型只看这些：

```text
客户端：会话 ID + 新问题
              ↓
服务层：恢复历史、构造上下文
              ↓
模型：依据有效上下文推理
```

运营商提供会话服务，是它替应用承担了部分状态管理，
不意味着模型权重自动获得了用户记忆。
如果推理状态可以继续使用，服务也可能恢复计算状态，而非从头重新计算全部历史文本。

### 推理引擎层

运行模型的推理引擎负责执行计算、管理 GPU 内存和调度请求，以及保存、复用、淘汰 KV 缓存。

边界按职责划分，不按公司划分：

- 云端 Agent 通常拿不到模型各层的 KV 张量，也不能控制引擎如何使用这些张量。
- 控制推理引擎的一方可以实现缓存，不限于模型厂商。
- 本地运行 Ollama 或 vLLM，同样可以由本地推理层管理计算缓存。
- 技术原理是公开的；云端某次请求的实际内部状态通常不对调用方开放。

## 三、为什么引出前缀缓存？

多轮交互中，输入往往重复很长的开头：

```text
第一次：[系统指令][历史][问题一]
第二次：[系统指令][历史][问题一][回答一][问题二]
```

如果每次从头处理相同前缀，就有重复计算。
前缀缓存复用已经算出的 KV 中间状态，减少这部分工作。

它属于推理优化，目标包括降低重复计算成本、缩短响应延迟，尤其是首个 Token 的等待时间，
以及提高吞吐量。缓存本身占用内存，并发收益需要结合容量和命中率评估。

### Token 数量、计算量与收费不是同一件事

| 概念 | 缓存命中后的变化 |
|---|---|
| 客户端上传内容 | 取决于 API，可能只上传新增内容。 |
| 模型有效上下文 Token 数 | 不因 KV 复用而减少，历史仍占用上下文窗口。 |
| 重复计算工作量 | 可以减少，但不等于历史完全不参与后续计算。 |
| 费用 | 取决于产品规则，可能对缓存输入优惠。 |

例如：历史 8,000 Token，新问题 100 Token。
如果完整历史仍作为上下文使用，总有效输入仍约为 8,100 Token。
命中缓存的历史前缀无需重复生成对应 KV，但新内容仍需要参考历史。

Token 是内容长度单位，不是计算次数单位。
真正减少有效上下文，需要筛选、截断、摘要或按需检索，而不是单纯保存历史或缓存 KV。

### 什么是“缓存输入”？

它不是一种新的输入格式，而是普通输入中命中了计算缓存的部分。
缓存输入与未缓存输入合起来仍是完整输入。
保存历史不等于命中计算缓存。

常见按 Token 计费的 API，可以分别对未缓存输入、缓存输入和输出定价。
部分产品还可能有缓存写入、存储或工具等费用，不能把一个公式视为所有产品的统一规则。
本地 Ollama 推理通常没有提供商的按 Token 账单，成本来自硬件、电力与运行资源。

一些 API 报告缓存用量。例如 OpenAI Chat Completions 的
`usage.prompt_tokens_details.cached_tokens`，以及 Responses 的
`usage.input_tokens_details.cached_tokens`。
调用方可据此核对账单，但这些数字仍由提供商报告，不构成独立审计其内部计算的证据。
耗时变快也不能证明某次请求一定命中了缓存。

## 四、KV 前缀缓存的实现原理

以下以常见因果 Transformer 和 vLLM 的公开实现为例。
不能据此认定所有运营商都采用相同数据结构。

### 1. 缓存中间结果，不是词语的固定含义

常见因果 Transformer 在各层计算 Key 和 Value。
推理引擎保存对应张量，供后续位置通过注意力机制使用：

```text
旧前缀 → 模型逐层计算 → KV 缓存
                           ↑
                   后续位置读取使用
```

一次生成过程中逐 Token 复用 KV，与跨请求复用相同前缀是两回事。
支持前者，不代表新的独立请求一定命中后者。

### 2. 匹配完整前缀，不是孤立 Token

```text
已有：[A B C D]
新增：[A B C D E F]
```

满足模型、配置、隔离范围等条件时，可以复用前四个位置。
但如果新增输入为：

```text
[X B C D E F]
```

即使 B、C、D 相同，它们前面的上下文不同，不能直接复用原来的对应 KV。

vLLM 按块管理缓存，缓存键可以概括为：

```text
块哈希 = Hash(前一块哈希 + 当前块 Token IDs + 其他相关条件)
```

前面变化，后面的哈希链随之变化。
这是精确前缀与计算条件匹配，不是语义相似匹配。
实际缓存机制还需要考虑哈希碰撞风险，以及模型、适配器、多模态输入和隔离条件等。

### 3. 为什么追加内容不影响旧 KV？

在这里讨论的因果模型中，一个位置只能关注自己及之前的位置。
末尾追加 E、F，不会改变 A、B、C、D 原有的计算依赖。
改动开头 A，则可能影响后面的所有位置。

这解释了为什么缓存通常复用连续的开头，而不是在后面任意找几个相同词语复用。

### 4. 命中后，历史仍参与计算

跳过的是重新生成旧前缀 KV 的重复处理。
新问题与新输出仍需通过注意力读取历史 KV：

```text
新位置的 Query
       ↓
与历史 Key 计算注意力权重
       ↓
结合历史 Value 得到结果
```

因此，历史没有退出计算，只是已有中间结果不必从头重算。
历史越长，仍可能增加后续计算与内存读取成本。

### 5. 用户数量庞大，缓存如何管理？

缓存不是永久保存所有历史，而是有限容量的近期计算结果池：

- 分块分配，便于共享和回收。
- 记录引用，保护正在运行的请求使用的块。
- 按策略淘汰不再使用的旧缓存。
- 管理过期和请求路由；请求到了没有对应缓存的实例，可能不命中。
- 根据租户或信任范围隔离，不能默认所有用户共享缓存。

缓存丢失只意味着重新计算，不应导致应用保存的会话历史丢失。

## 五、补充：KV 中的 Value 是 tensor 吗？

是。但要区分两个不同的 value。

### 缓存索引中的 value

从概念上看：

```text
缓存键：前缀哈希
缓存值：对应 KV 张量块的位置或引用
```

例如 vLLM 的哈希索引用于找到对应物理缓存块。
索引不需要把整块张量直接复制到普通键值表的 value 字段；
实际张量数据位于 GPU 等内存中，具体布局由推理引擎决定。

### KV 中的 V（Value）

K 和 V 本身都是张量，即具有形状的数值数组，不是文本或“词义”的字符串。
对于某层、某个注意力头、某个 Token，V 可以理解成一个数值向量：

```text
V = [0.12, -0.35, 0.87, ...]
```

这些数值只是示意。多个 Token、多个头的数据组合成更高维张量；
各层有各自的 K、V，实际布局也因实现而异。
后续位置根据注意力权重，对相关 V 做加权组合。

所以准确地说：

> KV 缓存保存模型各层的 K、V 张量；前缀索引帮助推理引擎找到这些张量。

“缓存表的 value”是数据结构角色，“注意力中的 Value”是模型计算概念，两者不能混为一谈。

## 六、与 Cosmos DB 等产品的区别

| 类型 | 缓存或保存什么 | 使用后的行为 |
|---|---|---|
| 前缀 KV 缓存 | 模型计算中间状态。 | 继续生成新回答，减少重复计算。 |
| 语义回答缓存 | 以前的问题及完整回答。 | 条件合适时直接返回旧回答，跳过本次生成调用。 |
| 会话存储 | 历史消息和业务状态。 | 恢复应用上下文，不自动带来计算缓存。 |

Cosmos DB 的语义缓存方案利用向量相似性检索来复用历史回答，不是管理模型内部 KV。
Azure API Management 配合 Azure Managed Redis 也可以提供语义回答缓存。
Redis 等还可用于精确请求的回答缓存，缓存键及失效策略由应用设计。

语义相似不保证旧答案可复用：权限、会话背景、实时数据或工具副作用不同，都可能让复用不适用。

前缀 KV 缓存应选择支持它的推理引擎或推理服务：

- 云端：使用模型 API 的 Prompt Caching 能力，按产品规则配置。
- 自建：vLLM 是明确支持自动前缀缓存的推理引擎之一。
- 当前 HanyingAgent：继续使用 Ollama，不为缓存另加数据库；
  是否跨请求复用及效果如何，需要针对实际版本、模型和请求验证。

KV 管理与模型执行、内存管理紧密结合，通常不是可接到任意 LLM API 前面的独立缓存产品。

## 七、VS Code + GitHub Copilot 中谁负责？

职责上：

```text
VS Code / Copilot：组织上下文、保持稳定前缀、设置缓存相关参数
                              ↓
推理提供方：判断命中、保存及复用 KV、管理过期
                              ↓
LLM：执行模型计算
```

VS Code 的官方技术说明介绍了对支持的 OpenAI 模型配置缓存保留策略，
以及对 Anthropic 模型设置缓存边界的做法。
实际 KV 不因此存放在 VS Code 本地；某次请求也不保证命中。
具体接口参数和支持条件会随产品版本变化，应以当前文档为准。

## 八、相关 LeetCode 练习

这些题练的是相关算法组件，不是直接实现 LLM KV 缓存。

| 题目 | 对应知识 | 与前缀缓存的关系 |

| [14. 最长公共前缀](https://leetcode.com/problems/longest-common-prefix/) | 判断序列共有的开头。 | 理解可复用部分需要从开头连续一致。 |
| [208. 实现 Trie（前缀树）](https://leetcode.com/problems/implement-trie-prefix-tree/) | 存储序列、共享前缀、前缀查找。 | 学习一种前缀索引结构；Token Trie 可使用 Token ID 而非字母。 |
| [146. LRU 缓存](https://leetcode.com/problems/lru-cache/) | 哈希表、双向链表、容量与淘汰。 | 理解有限容量缓存如何回收近期较少使用的数据。 |

建议顺序：14 → 208 → 146 → 460（选做）。

这些题不覆盖 KV 张量、GPU 内存、并发引用和租户隔离，只用于理解数据结构。

## 九、对当前学习范围的结论

Agent 管理信息与行动，推理引擎管理计算。
前缀缓存解决重复计算效率问题，不替代 Memory、Conversation 或 Context。

当前优先掌握 Session / Conversation、Memory / Context、Task / Orchestration 和受控工具闭环。
KV 内部实现暂不作为 HanyingAgent 的工作项。
以后优化延迟和费用时，再研究缓存命中与请求组织即可。
