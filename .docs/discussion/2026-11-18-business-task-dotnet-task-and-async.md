# 业务 Task、.NET Task 与异步执行模型

讨论日期：2026-11-18

本文整理阅读 LocalTaskManager 时关于任务生命周期、协作取消、线程池和 async/await 的讨论。
从简单 C++ 线程池的经验出发，建立业务任务与底层异步执行之间的对应关系。
文中的状态机和回调示意用于理解机制，不是编译器生成代码的精确实现。

代码入口：[LocalTaskManager.cs](../../HanyingAgent/SRC/Runtime/Management/Tasks/LocalTaskManager.cs)。

## 一、先区分四个层次

| 层次 | 职责 |
|---|---|
| 业务 Task | 表示用户提交的一次请求，管理 ID、会话归属、状态、结果和取消。 |
| Agent 主流程 / Orchestrator | 决定这次请求如何执行，组织上下文、模型调用和历史保存等步骤。 |
| .NET Task / Task<T> | 表示一次操作的完成，供调用方等待、获取结果或观察异常。 |
| 线程池 | 提供线程，调度当前可以执行的工作片段。 |

业务 Task 不是 .NET Task，.NET Task 也不是一个专属线程。

当前设计可以概括为：

> 业务任务管理包住 Agent 执行流程；.NET Task 和线程池提供底层执行机制。

## 二、从 C++ 简单线程池建立映射

最简单的线程池通常包含一组线程和一个工作队列：

```text
提交函数入口及参数 → 队列 → 空闲线程取出 → 调用函数
```

与 .NET 的概念对应：

| 简单 C++ 线程池 | .NET |
|---|---|
| 工作线程集合 | ThreadPool |
| 函数地址、参数或捕获数据的 lambda | 委托及其捕获的数据 |
| 提交工作 | Task.Run 等调度入口 |
| 工作队列 | 线程池内部工作队列，不保证全局 FIFO |
| 自己设计的完成状态、结果和异常通知 | Task / Task<T> 提供的完成观察能力 |

Task 在用途上更接近“可观察操作完成的句柄”，与 std::future 有相似之处，
但不能把两者的具体机制完全等同。

一个有用的心智模型是：

```text
工作入口：要执行什么
线程：谁来执行代码
线程池：如何派发可执行工作
Task：整次操作是否完成，结果或异常是什么
```

Task 不一定来自线程池。异步网络 I/O、定时器和手动完成信号等，都可以通过 Task 表示。
把 Task 传来传去，通常是在传递观察同一次操作完成情况的引用，而不是搬运线程。

## 三、SubmitAsync 是提交作业，不是等待作业完成

当前提交过程的关键代码是：

```csharp
var task = store.CreateTask(request, owner, clock.GetUtcNow(), cancellationToken);
var handle = new ExecutionHandle(owner);
_running.Add(task.Id, handle);
handle.Work = Task.Run(() => RunAsync(task, handle), CancellationToken.None);
return task;
```

这里形成两条逻辑执行链：

```text
Console 控制链：
    SubmitAsync → 创建业务记录 → 登记 handle → 派发工作 → 返回 TaskInfo
                                                    │
后台执行链：                                        └→ RunAsync
                                                        → 调用 Orchestrator
                                                        → 保存终态和结果
                                                        → 清理
```

- `await SubmitAsync(...)` 等待的是提交完成，取得 TaskInfo。
- `handle.Work` 表示整次后台执行的完成，包括收尾。
- `Task.Run` 不要求新建线程，通常复用线程池已有线程。
- 后台工作可能在 Task.Run 返回前就已经开始，不必等提交方法返回。
- 业务 Task 已有终态或结果，不一定意味着后台最后的清理代码也全部结束。

这里调用的是接收异步委托的 Task.Run 重载，返回的 Task 会跟踪内部 RunAsync 的完成，
而不只是跟踪“委托已经被调用”。

传给 Task.Run 的 CancellationToken.None 表示不通过该参数取消工作启动。
业务取消仍由 handle.Token 传入执行链处理，保证刚接受就被取消的任务也能进入收尾流程。

## 四、Task 保存在哪里，谁负责调度

当前进程中有两组不同的对象：

```text
业务记录：
    InMemoryAgentState.Tasks → TaskInfo
    InMemoryAgentState.Results → TaskResult
    由 InMemoryTaskStore 管理

执行跟踪：
    LocalTaskManager._running
        → TaskId
            → ExecutionHandle
                → Work：.NET Task
```

`_running` 是应用维护的执行跟踪表，不是线程池的调度队列。
线程池不会遍历它，也不认识业务 TaskId。

Task.Run 把待执行工作交给运行时调度，并返回 Task 引用。
即使应用不保存返回值，工作也仍可能正常执行；保存它是为了等待、跟踪异常和协调退出。

运行中的异步操作由运行时、等待中的操作和已登记的后续动作等保持必要的引用关系，
不是依赖我们的字典才能继续执行。
执行收尾后，管理器移除 handle 并释放取消源；对象不再被引用时，才可由 GC 回收。

当前业务记录和执行跟踪都在进程内存中，不提供重启恢复能力。

## 五、await 暂停的是执行链，不一定是线程

```csharp
var owner = await identity.GetUserIdAsync(cancellationToken);
// 后面的代码依赖 owner，必须等上面的操作成功完成。
```

两种情况需要分开：

1. 等待的操作已经完成：直接获取结果并继续，不必暂停。
2. 等待的操作尚未完成：保存执行进度、登记后续动作，当前方法暂停并返回代表完成的 Task。

如果外层也 await，那么外层执行链也会等待：

```text
获取身份完成
    → SubmitAsync 继续，完成提交
        → 外层取得 TaskInfo，继续执行
```

因此，“代码执行链停在 await 处”是正确理解。
异步没有消除前后依赖，也不让后面的代码提前执行；
它消除的是为了等待而必须占住一个线程的要求。

对于真正的异步 I/O，概念上更接近：

```text
登记：操作完成后，继续执行后半段
当前调用返回
```

而不是：

```text
当前线程停在这里，直到结果到达
```

async/await 不会自动消除底层同步阻塞。Task.Wait、Task.Result、Thread.Sleep
以及同步阻塞 I/O 等，仍可能占住线程。
最外层存在同步等待，也不意味着每条异步执行链都必须各占一个等待线程。

## 六、谁保存暂停位置：编译器生成的异步状态机

C# 编译器会把 async 方法改写为状态机，处理 await 的暂停和恢复。
概念上，它保存：

- 当前执行状态，即恢复后从哪里继续。
- 跨暂停点仍需要的参数和局部变量。
- 等待中的 awaiter。
- 用于报告方法结果或异常的辅助机制。

```text
执行到未完成操作的 await
    → 记录状态、保存必要数据
    → 登记完成后继续推进状态机的动作
    → 当前调用返回

操作完成
    → 触发后续动作
    → 推进状态机，恢复到相应位置
```

状态机负责“执行到哪里、接下来做什么”；返回的 Task 对外表示“整个方法是否完成”。
这不是把原来的调用栈冻结后交给另一个线程，而是将执行逻辑改写为可恢复的片段。

> 一个作业，多段执行；状态跟着作业走，线程负责执行当前这一段。

多个 await 可能形成多段，但已经完成的 await 不必产生一次新的调度。

## 七、数据回来后，谁让代码继续执行

以异步网络请求为例：

```text
网络数据到达
    → 操作系统通过 I/O 完成机制通知运行时
    → 网络组件处理数据，使相应操作完成
    → 触发 await 提前登记的后续动作（continuation）
    → 继续推进异步状态机
```

不需要找回原来那个线程，也不需要为每次网络等待专门留一个线程。

在当前后台执行环境中，后续代码通常由线程池线程执行；
有时也可以直接在处理完成通知的线程上继续，不一定每次重新入队。
其他环境可能有 SynchronizationContext 或调度器约束，因此不能推广为所有 await 都必然换到线程池。

多条执行链本来就可以由多个线程并发执行。
异步等待不是为了强制轮流执行，而是因为某条链正在等外部结果，没有代码可继续运行，
所以不必让它独占一个线程。

## 八、与线程上下文切换、等待锁的区别

### 不是操作系统线程上下文切换

| 对比 | 线程上下文切换 | 异步方法暂停与恢复 |
|---|---|---|
| 主要机制 | 操作系统调度线程 | 状态机、awaiter 和后续动作 |
| 保存对象 | 寄存器、栈指针等线程现场 | 方法继续执行所需的状态和数据 |
| 恢复方式 | 恢复该线程现场 | 推进状态机，执行后续代码 |

异步执行过程中也可能发生真正的线程上下文切换，但它们是不同层次的机制。

### 不同于等待普通 lock

普通 lock 发生竞争时，线程可能先自旋，再阻塞等待；不能把它当作 await 式让出。
而等待未完成的真正异步操作时，执行链可以暂停，不占住线程。

异步同步原语也存在，例如 `await semaphore.WaitAsync(token)`。
所以准确区别是“同步阻塞等待”和“异步非阻塞等待”，而非所有锁等待都一样。

## 九、Console 控制链与后台执行链

不宜把它们固定理解为“Console 主线程”和“某个工作线程”，因为异步执行可能换线程。

```text
Console 控制链：提交、查询、请求取消业务 Task
后台执行链：执行 Agent 流程，并维护执行期间的业务状态
```

后台 RunAsync 不只是一次 Orchestrator 调用，还包含：

```text
标记开始 → 检查取消 → 调用 Orchestrator
    → 处理成功 / 异常 / 取消
    → 保存终态、释放会话
    → 等待已触发的取消回调
    → 移除 handle、释放资源
```

双方通过共享对象协调。管理器的 `_gate` 保护执行登记和控制操作，
Store 的共享锁保护存储一致性；它们不是同一把锁。
CancellationToken 则提供线程安全的协作取消机制。

## 十、取消不是强行终止线程

ExecutionHandle 保存几类不同信息：

| 成员 | 用途 |
|---|---|
| Owner | 业务归属校验 |
| Token | 将取消信号传入后台调用链 |
| Work | 表示后台执行的完成 |
| CancellationCallbacks | 表示已触发取消回调的执行完成 |

取消链路是：

```text
/cancel
    → LocalTaskManager.CancelAsync
    → Store 请求业务状态变更
    → 找到 handle，调用 handle.CancelAsync
    → CancellationTokenSource.CancelAsync
    → Token 进入已请求取消状态
    → 检查点或支持取消的 API 响应取消
    → RunAsync 处理取消并收尾
```

`ThrowIfCancellationRequested()` 在执行到该行且 Token 已取消时抛出异常。
它不是强制中断任意代码，也不会让已经经过的检查点回头执行。
客户端取消网络等待，也不保证远端模型立刻停止推理。

CancellationCallbacks 初始为 Task.CompletedTask：

- 未触发取消时，收尾 await 它会立即通过。
- 触发取消后，它保存取消源 CancelAsync 返回的 Task，收尾等待回调执行结束。
- 它不是业务 Work，回调结束不等于业务执行结束。
- 管理器 CancelAsync 等待回调，不等于等待整个后台作业退出。

RunAsync 不是一直停在 await callbacks 等用户取消；
它先执行主体，随后在收尾阶段等待已经触发的取消回调。

CancelAsync 不立即从 `_running` 删除 handle，
否则等待结果、Host 退出和资源释放会失去跟踪依据。
最终移除和 Dispose 由 RunAsync 收尾负责。Dispose 本身不表示请求取消。

## 十一、生产者—消费者与后续扩展

当前机制具有“提交工作、后台处理”的特征，但没有应用自己管理的显式任务队列：

```text
接受请求 → Task.Run 直接派发 → 后台执行
```

线程池内部有工作队列，但它不理解模型服务并发上限、业务优先级和积压策略。
当前同会话忙时拒绝提交，不进行业务排队，也没有全局并发上限。

需要控制积压、突发请求和并发时，可以演进为：

```text
提交请求 → 有界 Channel 队列 → 若干 Worker → 执行现有业务流程
```

但这不是当前必须实施的改造：

- 只限制并发，不一定需要显式队列。
- 引入队列后，还要设计排队取消、满队列行为和退出时的待执行任务处理。
- 进程内队列本身不提供重启恢复；持久化调度是另外的需求。

## 十二、最终心智模型

写业务代码时，先关注三个问题：

1. 这个 Task 表示哪次操作的完成？
2. 谁负责 await、取得结果和观察异常？
3. 取消信号怎样传递，资源由谁收尾？

理解调度或排查性能时，再下潜到线程、工作队列和 I/O 完成机制。
不需要每写一行异步代码，都在脑中完整模拟底层线程切换。

> 业务 Task 管理请求的生命周期；Orchestrator 组织 Agent 主流程；
> .NET Task 表示操作的完成；状态机保存执行进度；线程池调度可执行片段。
